A deployed zero-delta precedent is [qualify-accepted-carrier-source metadata](https://github.com/royhsu-work/investment-strategy/blob/f327e5f7f054affa40120c8ca93a2804032a3f25/openspec/changes/archive/2026-11-26-qualify-accepted-carrier-source/.openspec.yaml).

Consolidate action-local methods, not standards. REUSE canonical requirements/config, semantic adapter, codebase-design, TDD, skill-creator and executable model; CONSOLIDATE duplicated procedural instructions; NO-DELTA for roles' independent gate ownership, current approval/routing/validation, CI, lifecycle, and production code. Adding standards, a checklist, evaluation service, separate reviewer call or extra gate would neither address the method defect nor preserve existing authority. Keep the main flow compact, load existing resources when relevant; extract nothing without demonstrated reuse. No modifications to the vendored skill-creator or shared engineering Skills.

## D3 — OpenSpec Review: Derive, Conformance, Challenge, Trace, Decide

Rewrite the current procedure as a compact executable flow, preserving Role authority and exact B/R preflight, current Human freshness, applicable config/canonical/adapter and exact validation.

1. **DERIVE:** Before relying on candidate claims, independently reconstruct the approved outcomes, invariants, exclusions, acceptance consequences, applicable same-Issue Explore and sources, and relevant exact baseline/review revision. Distinguish source facts, inference and unresolved claims.
2. **CONFORMANCE:** Inspect each artifact against its responsibility (proposal why/what/scope; delta externally verifiable normative behavior; design structure, ownership and tradeoffs; tasks observable implement/verify slices). Use existing config/adapter rather than copying their rules. Check complete applicable delta blocks, surviving MODIFIED scenarios, canonical Purpose, explicit valid zero-delta semantics and scope. Strict GREEN cannot excuse responsibility errors.
3. **CHALLENGE:** For every material semantic boundary derived above, test each material acceptance predicate with the smallest discriminating case that could change PASS to FINDINGS; compare the candidate with simpler ownership/interface/vertical slice alternatives where relevant through an actual caller or observable consequence. Reuse a case across boundaries only when its evidence actually discriminates each predicate. Do not let success on one boundary substitute for another. Use existing codebase-design guidance and current N-1 constraints to reason concretely about executability, testability, reviewability, mergeability and deployability. Examine counterexamples and alternatives (e.g. failure, competing ownership, replay). Fold former REALIZE and CLOSE into the investigation: bind evidence to actual substrate and exact time/revision/provenance; separate current/candidate/future/unavailable proof; establish disposition of competing responsibilities for removal/reuse/consolidation/no-delta. Close design-level consequences here, code-level closure in Implementation Review. Harmless alternatives are not findings.
4. **TRACE:** Check reverse-first tasks → design → specs → proposal, then forward proposal → specs → design → tasks; use canonical context for a legitimate zero-delta change. Check upstream source support and Skill maintenance declarations, not just internal consistency.
5. **DECIDE:** Use the Action's existing legal results and evidence/closure rules; only accept an exact revision when its material gate is met. Missing or contradictory evidence cannot be accepted. Preserve existing findings/Human decision paths, staged coverage, independent review and no mutation/successor authority.

## D4 — Implementation Review: Derive, Inspect, Challenge, Verify, Refactor, Decide

Preserve current exact open-head versus closed+merged historical-head/current-default dual-identity preflight, scope, finding history, Human freshness and revision-binding. Then:

1. **DERIVE:** Independently reconstruct expected behavior and observable closure from approved exact semantic context, existing findings and applicable invariants. Do not use Executor tests as the oracle.
2. **INSPECT:** Trace real affected caller/interface through actual production owners to effects/outputs; inspect diff and affected tests, including changed and competing owners. Identify observable outcomes, not private-call counts.
3. **CHALLENGE:** Actively construct the smallest contrasting input, negative/boundary/failure case or alternative that discriminates against the independently derived expectation. Seek uncovered caller-visible failures, use actual safe caller probes with I/O substitutions when supported, or inspectable source/CI evidence when appropriate; distinguish actual failure from unavailable proof. Never fabricate a probe, run, or regression.
4. **VERIFY:** Verify actual intended pre-implementation RED and minimum GREEN chronology for executable work, source-bound exact CI, public seam and independent oracle, full existing quality, exact validation, approved task markers/checkpoints, stage coverage, Human freshness, Skill declaration and procedural semantic cases where applicable. Static/setup/import/fixture/unrelated failure is not RED; retrospective tests do not establish Test First. Review protected behavior, not merely test count.
5. **REFACTOR:** Independently inspect the affected responsibility/interface boundary, cohesion, coupling, locality, duplication/SSOT, unnecessary abstractions and affected tests. Apply codebase-design and TDD knowledge, remove → reuse → consolidate → existing owner; assess test retirement against equivalent-or-stronger coverage or authoritative retirement. Use existing in-scope requirement/evidence/closure criteria, with no mandatory pattern or new gate.
6. **DECIDE:** For this Action, implementation defects are FINDINGS for Executor, specification defects SPEC_BLOCKER for Lead's resolve-question, reserved decisions HUMAN_DECISION_REQUIRED, unqualified evidence BLOCKED as applicable, and PASS only when existing exact gate is met. Preserve original observable closure when evaluating alternative corrections/counterevidence, review corrected exact head independently, never edit the review target, and retain advisory items without blocking. The model derives successors. Do not change Archive Review results or authority.

## D6 — Evaluation: actual before/after decisions, not phrase counts

Use the repository-vendored [skill-creator](https://github.com/royhsu-work/investment-strategy/blob/f327e5f7f054affa40120c8ca93a2804032a3f25/agents/skills/skill-creator/SKILL.md) and [integration guidance](https://github.com/royhsu-work/investment-strategy/blob/f327e5f7f054affa40120c8ca93a2804032a3f25/agents/skills/skill-creator/references/repository-governance.md): generalize feedback, keep prompt lean, explain purpose, smallest sufficient edit and genuine reuse. Before editing each mapped Skill, freeze the exact old Skill and applicable config/adapter/canonical/engineering inputs at the slice preimage. Prepare fixed neutral representative inputs with expected discriminations derived from the actual contracts, separately from the reviewer prompt. Use identical input bytes before/after; do not announce defect, answer key or desired result. Record actual decisions, consulted input revisions, action sequence, actual supporting evidence/counterexamples, and disposition/closure in existing delivery evidence. Compare actual detection, false positives and missed protections, including controls; refine on these developmental cases. This establishes known-case regression evidence, not independent discovery.

OpenSpec discriminators: independently distinguish strict-valid proposal responsibility violations and strict-valid delta responsibility violations from conforming artifacts (both defect classes, not either/or); distinguish an otherwise coherent plan with one challenged material acceptance boundary but another left unexamined from one with sufficient evidence for every material predicate; internally traceable proposal whose coupled delivery cannot satisfy a demonstrated current N-1 boundary versus an independently verifiable alternative; unsupported source/owner/chronology claim versus supported claim; legitimate zero-delta or complete MODIFIED plan and a harmless architectural preference. Implementation discriminators: exact-green implementation with a missed caller-visible defect (e.g. malformed versus complete input with unchanged oracle); concrete duplicated responsibility/obsolete test assumption versus unique regression; specification defect versus implementation defect; intended pre-implementation RED versus setup/static/retrospective failure; correct implementation, harmless advisory, and missing evidence. Use neutral task prompts with actual immutable source evidence or explicit representative synthetic fixtures; never present synthetic runs as repository CI. Include passing controls for both procedures. Assess actual findings/closure, supported decisions and evidence, not word counts or checklist completion.

After the developmental comparisons, freeze the candidate Skill bytes and applicable inputs for both methods. The existing independent Implementation Review owns the final assessment of independent discovery: exercise the frozen candidate as review work product, not as active repository governance, on previously unused discriminating cases relevant to the material outcomes above, including valid and harmless-advisory controls. Select previously unexamined source-backed review targets or independently prepared neutral fixtures whose defect labels, answer keys and expected decisions have not been supplied to the evaluated reviewer; do not repeat the author's cases as novel evidence. Present the ordinary review task and source/contract context, not a hinted defect. Capture the actual decisions, observed evidence and closure before comparing with separately derived contract-based expectations. Bind the record to exact candidate Skill/context, case identity, prior use and available context/exposure evidence. Use independent derivation of the expected result, not agreement with the author as an oracle.

No blind subagent/benchmark facility is established for this connector path. Use the existing later independent Reviewer invocation with demonstrably fresh case material and available context separation or equivalent evidence; no new evaluator, model call, gate or hidden state. A context-aware run on a known answer, including a case the evaluated reviewer authored with its defect already identified, is rehearsal even if the immediate prompt is neutral. If a fresh unprompted case and its answer exposure cannot be established, record the limitation, do not count it as independent discovery or waive the approved outcome; disposition the actual defect or unavailable evidence through the existing finding/blocking contract. The reviewer retains existing authority and checks both methods before PASS. Do not claim a blind benchmark, generalization beyond observed cases, actual executable RED, or future CI PASS. If executable behavior becomes necessary, return to the applicable authority boundary and use actual source-bound Test First; do not smuggle a new executable mechanism into zero-delta work.
