1. **CONSOLIDATE — development vs completion.** Use existing typed ingress and application-owned materialization for both consequences. Determine consequence from the actual authorized effect and task-marker delta, not a worker-asserted test mode or commit message: a development-only manifest preserves completion markers and has no completion/checkpoint/routing/merge effects; a completion manifest/obligation must establish the first incomplete slice's verified completion criteria. Existing worker result vocabulary remains; development ingress is not a committed formal slice result. Application owns exact preimage, immutable acceptance for each authorized physical effect, fresh reauthorization, non-force materialization, carrier postconditions, and release of a settled development attempt. Do not reinterpret historical completion ACCEPTED as development. No new ownership store; reconstruct current first incomplete slice, exact commits, accepted intent and CI evidence using existing proof owners. An accepted development attempt with settled physical writes and qualified terminal CI (PASS or FAIL) releases that attempt's current ownership without formal result or routing mutation. Pending CI is a bounded observation, not a new state. Unknown/unsettled/competing writes retain their protection. Reuse current-frontier reducer in Dispatch and Phase A; distinguish physical write authorization from completion authorization. Completion produces exactly one effective checkpoint and formal completion result; use existing completion result and successor model only at completion.
2. **REUSE — native CI.** Existing Python Quality workflow, checkout exact candidate head, Ruff lint -> Ruff format --check -> Mypy -> pytest; use native step failure semantics. No local execution assumption, special entry, mode, runner or extra verify run when exact GREEN meets all criteria. Preserve exact checkout/run/attempt/gate evidence (not run.head_sha alone). Ensure task-only completion revisions trigger the same Python Quality workflow: extend existing path filter to active Change tasks.md; do not inherit older HEAD PASS. Keep existing Strict OpenSpec gate where applicable; integrate the shared Task Contract check described in decision 6 into that same exact mechanical gate. Focused intended behavioral test is included in normal pytest; actual output must distinguish expected target failure from syntax/import/fixture/setup/dependency or unrelated failure. Static checks must all pass first. Correct mechanical non-RED defects in the same slice; do not claim RED. Minimum production change then full exact GREEN, refactor only when needed and revalidate new revisions. Task markers may be materialized after verified implementation evidence, but formal completion is not authorized until the resulting exact HEAD also passes all required gates and postconditions. Persist one checkpoint/result before next slice/handoff. Use ordinary CI and native events, not direct Actions execution.
3. **REUSE — normal correction vs Recovery.** Keep acceptance bound to exact intent and candidate. Pending/unknown/canceled/conflicting verdicts cannot prove completion; unresolved writes or competition protect admission. Known ordinary mechanical failure does not itself create a recovery obligation. Specification defects and Reviewer findings use existing correction/review boundaries.
