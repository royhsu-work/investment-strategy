## Decisions

1. **CONSOLIDATE — development vs completion.** Use existing typed ingress and application-owned materialization for both consequences. Determine consequence from the actual authorized effect and task-marker delta, not a worker-asserted test mode or commit message: a development-only manifest preserves completion markers and has no completion/checkpoint/routing/merge effects; a completion manifest/obligation must establish the first incomplete slice's verified completion criteria. Existing worker result vocabulary remains; development ingress is not a committed formal slice result. Application owns exact preimage, immutable acceptance for each authorized physical effect, fresh reauthorization, non-force materialization, carrier postconditions, and release of a settled development attempt. Do not reinterpret historical completion ACCEPTED as development. No new ownership store; reconstruct current first incomplete slice, exact commits, accepted intent and CI evidence using existing proof owners. An accepted development attempt with settled physical writes and qualified terminal CI (PASS or FAIL) releases that attempt's current ownership without formal result or routing mutation. Pending CI is a bounded observation, not a new state. Unknown/unsettled/competing writes retain their protection. Reuse current-frontier reducer in Dispatch and Phase A; distinguish physical write authorization from completion authorization. Completion produces exactly one effective checkpoint and formal completion result; use existing completion result and successor model only at completion.
2. **REUSE — native CI.** Existing Python Quality workflow, checkout exact candidate head, Ruff lint -> Ruff format --check -> Mypy -> pytest; use native step failure semantics. No local execution assumption, special entry, mode, runner or extra verify run when exact GREEN meets all criteria. Preserve exact checkout/run/attempt/gate evidence (not run.head_sha alone). Ensure task-only completion revisions trigger the same Python Quality workflow: extend existing path filter to active Change tasks.md; do not inherit older HEAD PASS. Keep existing Strict OpenSpec gate where applicable. Focused intended behavioral test is included in normal pytest; actual output must distinguish expected target failure from syntax/import/fixture/setup/dependency or unrelated failure. Static checks must all pass first. Correct mechanical non-RED defects in the same slice; do not claim RED. Minimum production change then full exact GREEN, refactor only when needed and revalidate new revisions. Task markers may be materialized after verified implementation evidence, but formal completion is not authorized until the resulting exact HEAD also passes all required gates and postconditions. Persist one checkpoint/result before next slice/handoff. Use ordinary CI and native events, not direct Actions execution.
3. **REUSE — normal correction vs Recovery.** Keep acceptance bound to exact intent and candidate. The existing F1 ownership rule excludes a settled exact FAIL with no committed Formal Result before cardinality reduction, preserving immutable ACCEPTED and effect history. Dispatch and Phase A use the same predicate; zero current owners and no competing ingress permit fresh same-Action correction. For a development attempt, settled writes plus a qualified terminal verdict permit next development or completion; for an existing completion candidate, an exact PASS remains subject to all completion gates, and an exact FAIL releases only its current ownership after settlement. Pending/unknown/canceled/conflicting verdicts cannot prove completion; unresolved writes or competition protect admission. Known ordinary mechanical failure does not itself create a recovery obligation. Specification defects and Reviewer findings use existing correction/review boundaries.
4. **CONSOLIDATE — recovery proof.** Evaluate current postconditions before mutation deduplication. Reuse the existing proof owner and causal evidence identity: historical digest equality cannot block read-only observation. Recover only unfulfilled durable obligations, never replay completed effects, manufacture historical evidence, rewind a completed descendant or authorize a conflicting replacement when writes are unknown. Legacy manifest/target differences require qualified lineage or existing legal correction. Separate Original, Formal Result and successor obligations; rollover preserves identity.
5. **N-1 delivery (one release, three vertical slices).** Current main cannot self-authorize RED development materialization. Human explicitly approved one bounded independent maintenance bootstrap on existing PR #479 after corrected artifacts and independent exact-R OpenSpec PASS (7163684737 / event 37256073447). Before any maintenance write independently qualify the concrete connector exact-preimage capability and legal maintenance activation; use only existing branch, native CI, preserved review/merge gates and no force or direct main mutation. This authorization does not activate the proposed future contracts, grant automatic merge or authorize a new maintenance workflow. Reconciliation to native lifecycle must be independently qualified under then-current governance. No new mandatory outcome is deferred: slice 1 development/completion + same-Action FAIL; slice 2 fresh Recovery proof; slice 3 legacy compatibility and end-to-end gates. Each slice has independently observable RED/GREEN/VERIFY criteria; no partial deployment or parent completion before all slices and release gates. The first bootstrap RED needs the static-first CI configuration as test infrastructure, not the runtime behavior under test: put the CI ordering setup and focused behavioral tests in the initial development revision, run native CI before production Runtime correction, and verify order/fail-fast separately from the target behavioral RED. Do not claim a passing configuration assertion as RED. If no qualified exact-preimage maintenance or native reconciliation path exists, surface that specific boundary rather than invent authority.
