## Engineering basis and selected design

The latest [Human decision](https://github.com/royhsu-work/investment-strategy/issues/496#issuecomment-7217540806) corrects the previous #478 description of checkpoint as completion evidence. [Prior PASS withdrawal](https://github.com/royhsu-work/investment-strategy/pull/497#pullrequestreview-6087714928) is review evidence, not a prescribed solution. A snapshot's identity is immutable; the saved work is not frozen. [Git snapshots](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository) supply durable version history, [GitHub exact-SHA required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) gate delivery, [Bazel hermeticity](https://bazel.build/concepts/hermeticity) illustrates reuse only for the same relevant inputs, and [Kubernetes controllers](https://kubernetes.io/docs/concepts/architecture/controller/) illustrate observing actual work rather than replaying history. These are engineering analogies, not additional repository gates or proof of candidate implementation.

REMOVE mandatory checkpoint-as-completion publication and its competing predicate. REUSE Git snapshots and the already existing content-addressed Application/Carrier operations. In N-1 application_materialization.py:2168–2234,2692–2746, the existing materialization proof distinguishes original W and current T, proves exact changed paths and allows later authorized descendants even if the original desired blobs have changed. This is the right persistence seam. The three commits of this exact maintenance PR (historical `e2def924`, `a6fff28`, `aefe8260`) demonstrate durable revisable artifacts, not normal scheduled authority or implementation RED. Unreferenced blobs alone are not sufficient durability; no progress comment or new registry is required for a saved commit. An accepted effect alone is not a saved commit. Neither Git ancestry alone nor current matching bytes proves the original authorized write. Existing proof and fresh observations remain required.

Reject (a) keeping completion plus checkpoint as two mandatory acceptance records, (b) adding a checkpoint phase/state or adopting a new workflow engine, and (c) a separate failed-checkpoint recovery protocol. Use the existing Application/Carrier as save owner, existing task/artifact verification owners for their relevant inputs, and the existing formal consequence owner for delivery. Do not transfer checkpoint gating under a new name.

## Decisions

1. **CONSOLIDATE — shared persistence and continuation.** An authorized save is a bounded content-addressed operation on the current qualified carrier, with the existing exact repository/Issue/Change/source authorization, manifest, path/blob and expected preimage, non-force mutation and fresh readback. The saved revision is a checkpoint regardless of later verification status. It can contain incomplete or failed work. Reconstruct its physical witness, current content and remaining work from the existing Git/PR/accepted-effect sources; no new checkpoint database, counter, lock, timer, per-save comment or workflow state. Legal later changes to the same paths are new authorized commits, not replay; old W and old evidence remain immutable. Do not redo still-valid saved work. A save does not grant correction authority outside the current role/approved scope, and neither the worker nor the save selects a successor.

   For this helper's normal implementation ingress, the existing Executor implement-change MORE_IMPLEMENTATION_REQUIRED envelope with exactly one authorized application-materialize effect and no completion effects is a physical-only save, not a formal result. Code/test writes preserve normative OpenSpec and task markers; a separate monotonic marker-only save is allowed after the current implementation criteria and gates pass (D4). No mixed code+marker manifest, completion comment, PR readiness, routing, merge or terminal effect in this physical-only shape. Do not silently strip disallowed effects. Preserve the existing exact carrier/first-carrier/supersession and historical accepted reconciliation protections; no new external worker flag, Action or ResultKind.

   **Shared interface for Propose.** The same existing materialization and observation proof consumes authorized content on a qualified carrier, independent of whether its paths are code or approved OpenSpec artifacts. Validate the shared save/reconstruct behavior on authorized Lead artifact and Executor content inputs at the real materialization/Carrier seam; a later authorized same-path revision must retain W, with current input-qualified evidence evaluated separately. This does not activate a pre-activation Lead partial-write lane in this helper: N-1 application_materialization.py:246–295 requires first `Change: unset` materialization to create new paths and does not provide a reusable partial carrier for unset; effect_contract.py currently binds READY_FOR_OPENSPEC_REVIEW to materialization, and full strict is a formal gate. #473 owns the artifact-specific admission/carrier construction before first activation, per-artifact applicable native validation, durable source/dependency evidence and completed-artifact reporting, including the actual pinned CLI experiments. It must compare durable referenced blob ingress and existing incremental Git materialization rather than assume an unreferenced blob or new Issue is sufficient. Do not change unset routing or authorize a new worker operation from this proposed design. Its whole mandatory outcome, including work-conserving same-Action continuation, is not optional or completed by this helper.

   For #473, artifact-local applicability is determined by the existing spec-driven DAG and declared capabilities/skip_specs, not by file count or checkpoint. Bind reusable validation to the exact artifact content, all materially relevant upstream, canonical, config and validator identities; retain output and source proof. Changed relevant input invalidates affected evidence, not unrelated valid artifacts; checkpointing alone gives no authority for backwards semantic edits. Persist and report successful artifact-local completion only after its applicable verification and readback; saving incomplete/failed bytes does not report success. Preserve final complete artifacts, bidirectional traceability, exact-R strict, independent review and lawful semantic correction. No mandatory full Python CI per Propose artifact, no new progress graph. Full #473 delivery remains tracked there.

Ordinary push/PR qualify only same-repository native event, exact target checkout R, required workflow definition/steps and attempt; a reusable invocation additionally binds the exact source DISPATCH_REQUEST, bridge run/attempt, plan job output/log and callee job identity, callee definition B and exact checkout R. For multiple eligible runs, reduce qualified observations for the same exact gate: terminal qualified PASS is reusable for an affirmative gate only when no contradictory qualified FAIL remains; an ordinary qualified FAIL is a correction verdict, not a reason to retry for PASS. Identical qualified verdicts from multiple runs are equivalent, not multiple authorization owners. A later run/attempt does not erase an earlier source-qualified terminal verdict used for historical settlement; current affirmative gates must independently qualify current required evidence. Bind the used run/attempt and actual checkout/steps, qualify each required component, do not mix attempts or silently ignore missing pages.

Once the exact prior caller/attempt is authoritatively terminal, its complete native job list and recorded plan distinguish skipped/not-invoked, canceled/no-verdict and completed qualified verdict. New call correlation derives from the existing accepted obligation and current native source request/run/attempt; native scheduler owns the job graph. An ordinary quality push/PR arriving concurrently is harmless read-only duplicate evidence, never a second materialization owner; qualify both rather than relying on latest-run preference. GitHub documents token-triggered push may not schedule another run ([triggering workflows](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)).

   The bridge emits its one existing non-authorizing NO_WORK result with reason `verification-obligation-pending` (never `no-routed-work`, so no idle admission) when observing/calling the gate; no Action or semantic result from that wake.
