## Engineering basis and alternative selection

Human's approved [#478 convergence](https://github.com/royhsu-work/investment-strategy/issues/478#issuecomment-7163243974) separates Commit (version control), Slice (delivery), and Checkpoint (completion evidence), permits normal exact mechanical FAIL correction, preserves exact marker HEAD gates, and rejects new runtime state or strong transaction ordering. The previous plan still accepted a multi-effect completion before the actual marker HEAD passed. This is the avoidable coupling exposed by [re-review F1b](https://github.com/royhsu-work/investment-strategy/pull/497#pullrequestreview-6087478390), not a need for a special failed-completion state.

Engineering practice: [Google small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) and [Google SRE release engineering](https://sre.google/sre-book/release-engineering/) distinguish reviewable source changes from reproducible release gates. [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) bind acceptance to the latest required SHA; [GitHub drafts](https://docs.github.com/en/pull-requests/reference/pull-requests) allow candidate work before merge. [Azure stage checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals) gate a consequential stage before it starts, not every earlier candidate write. [Kubernetes controller](https://kubernetes.io/docs/concepts/architecture/controller/) and [AWS redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html) illustrate reconstructing actual outstanding work and preserving settled operations. [OpenSpec apply/verify](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md) distinguishes task progress from verifying the whole change; current upstream docs are external practice, not authority over our pinned version or extra delivery gates.

Alternatives: (a) suspend/supersede a prematurely accepted marker+checkpoint+result bundle on ordinary FAIL, which retains a needless future publication obligation and competing ownership; reject. (b) validate a speculative marker commit before updating the existing carrier, which needs an independently qualified unreferenced-commit checkout or another staging ref and duplicates candidate handling; do not depend on an unproven platform capability or extra branch. (c) use the existing implementation branch as the candidate staging surface, authorize only the effect that is presently justified, and authorize completion publication after actual exact-head verification; select. This is an operation boundary change inside the existing Application, not a new workflow or TDD stage machine. D1/D4 replace the old bundle contract, D2/D3 retain their shared quality and settlement ownership. No need to adopt a workflow engine, outbox database, separate approval protocol or incident-specific recovery branch.

## Decisions

1. **CONSOLIDATE — application consequence owner.** Reuse existing typed ingress, effect contract, authorization and exact materialization. There are two consequence boundaries for new implementation work, not two lifecycle states. An Executor implement-change MORE_IMPLEMENTATION_REQUIRED payload containing exactly one authorized materialization and no completion effects is physical-only. Code/test/development infrastructure changes preserve task markers and normative OpenSpec content; a marker-only materialization is allowed only after independent qualification of the current implementation's full native gates and exact slice criteria under D4. Never combine code changes and marker delta or treat a marker write as a formal result. A physical-only ACCEPT contains no checkpoint, ACTION_RESULT, PR-ready, routing or merge obligation; it settles on exact physical proof and its own terminal native verdict under D3. The existing typed result is an ingress carrier here, not a committed formal MORE_IMPLEMENTATION_REQUIRED.

   A publication-only READY or MORE_IMPLEMENTATION_REQUIRED is accepted separately, only after the existing owner proves the current logical slice, already durable authorized markers and current exact required PASS. It has no materialization effect and cannot generate a new ref or no-op commit; Application derives the canonical checkpoint/result and existing successor and (where READY applies) retains existing PR readiness requirements. The same owner validates complete input, immutable source, scope, fresh Human/review/carrier/preimage and effect postconditions. Reject mixed, unauthorized or incomplete shapes, never silently drop an original effect. Historical accepted bundles and established first-carrier/supersession/merged reconciliation retain original meaning and existing guards. No new Action, ResultKind, worker flag, state or store.

Replace the proposed second asynchronous `workflow_dispatch` POST with a local reusable workflow call: add `workflow_call` to this same existing workflow (no separate workflow/runner/test mode), exact target repository/revision, verification correlation, and producer/checkout/run-attempt proof inputs. In the existing `scheduled-agent-bridge.yml`, the bridge planning job emits an application-derived outstanding verification target only when the shared validation-resource/frontier owner qualifies it from current source and complete run/job evidence. Expose that plan through native job outputs; a conditional dependent job uses `./.github/workflows/quality.yml` with those outputs, contents: read, no inherited secrets and checkout persist-credentials: false. The caller is already the source-bound native DISPATCH_REQUEST run; no second POST, response, separate run identity or ambiguous acceptance window. The callee uses the caller's definition commit, not a worker-supplied ref; compare native caller definition SHA, actual planner checkout B and qualified current main B before scheduling, reject stale definition/plan. GitHub documents local reusable calls use the same commit as caller, pass job outputs via needs, and cannot elevate permissions ([Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows), [configuration reference](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations)). Current bridge already uses native source request correlation, Actions access, exact current checkout and outputs; N-1 test-only push/PR supports development of the proposed integration, not candidate self-authorization.

   The one shared verification owner takes the exact outstanding gate (repository, Issue/Change, immutable accepted source/effect, required revision, qualified producer contract) and completely reads both normal quality push/PR runs and existing bridge source runs, attempt-specific jobs and logs. Reuse counted-page proof from `issue_comment_bridge._complete_workflow_runs` (event filter generalized for the two native sources) and existing source/run/artifact/checkout proof primitives. Ordinary push/PR qualify only same-repository native event, exact target checkout R, required workflow definition/steps and attempt; a reusable invocation additionally binds the exact source DISPATCH_REQUEST, bridge run/attempt, plan job output/log and callee job identity, callee definition B and exact checkout R. Native run metadata, a prior attempt, unrelated job, claimed outputs or a mere run title cannot establish a verdict. Preserve authoritative B-owned verification for ordinary R; where R changes the required workflow definition, its separate candidate-side producer/contract proof remains applicable (candidate push/PR uses its definition; a B-owned called job does not claim to exercise R's new definition). Candidate CI remains read-only and the current default branch owns privileged validation. For multiple eligible runs, reduce qualified observations for the same exact gate: terminal qualified PASS is reusable for an affirmative gate only when no contradictory qualified FAIL remains; an ordinary qualified FAIL is a correction verdict, not a reason to retry for PASS. Identical qualified verdicts from multiple runs are equivalent, not multiple authorization owners. A genuine observed mechanical FAIL and PASS on separate eligible executions is a negative affirmative gate and permits normal corrective development, not selection of a convenient PASS or permanent mutation Recovery. Distinguish that from contradictory facts about a single run/attempt or its source, which fail closed. A later run/attempt does not erase an earlier source-qualified terminal verdict used for historical settlement; current affirmative gates must independently qualify current required evidence. Bind the used run/attempt and actual checkout/steps, qualify each required component, do not mix attempts or silently ignore missing pages.

   If a native invocation is active or the already qualified source run/attempt or job inventory is incomplete/not-yet-visible, bounded observation only, no new call. Once the exact prior caller/attempt is authoritatively terminal, its complete native job list and recorded plan distinguish skipped/not-invoked, canceled/no-verdict and completed qualified verdict. Bind the proof to the attempt that actually ran the plan and job; a later attempt cannot borrow earlier job outputs or erase the historical verdict used by a proven successor. A terminal prior caller with no eligible verdict or active call allows a later fresh qualified dispatch run to invoke the same read-only quality job; no attempt to infer non-execution from a missing API response. New call correlation derives from the existing accepted obligation and current native source request/run/attempt; native scheduler owns the job graph. An ordinary quality push/PR arriving concurrently is harmless read-only duplicate evidence, never a second materialization owner; qualify both rather than relying on latest-run preference. A missing push on GITHUB_TOKEN application materialization or marker-only revision is handled by the same fallback. GitHub documents token-triggered push may not schedule another run ([triggering workflows](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)).

   The bridge emits its one existing non-authorizing NO_WORK result with reason `verification-obligation-pending` (never `no-routed-work`, so no idle admission) when observing/calling the gate; no Action or semantic result from that wake. For an intended quality FAIL the native called job and possibly the aggregate bridge run fail normally; do not weaken the required successful-run check for consuming AUTHORIZE, turn the called job failure into success, or consume that failed run as a semantic dispatch. The existing consumer may read the already-uploaded NO_WORK artifact as non-authorizing audit only when the planner job, artifact, run/attempt and native required job outcome are independently qualified; an aggregate failed run never supplies AUTHORIZE or idle admission. No extra result schema, lock, retry count, queue, or independently triggered workflow. An unqualified caller cannot schedule a job or authorize semantic work.
