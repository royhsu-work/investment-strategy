## D2 — Per-behavior TDD and independent refactor ownership

For executable behavior choose a small public seam (caller-visible result, contract, error or observable effect); prefer real in-process collaborators and use suitable adapters at genuine I/O or other substitution boundaries. Do not expose internals solely for tests; a test double must implement the interface it replaces. A meaningful test has independent expected behavior. Within a delivery Slice, iterate one observable behavior at a time: introduce its failing test, qualify intended RED using source-bound CI evidence, implement only enough behavior, obtain GREEN, repeat. A setup/import/syntax/static or unrelated failure is not intended RED, and a later-written test does not establish Test First. Use actual CI on the repository-supported execution substrate, not a local dependency assumption. Distinguish test cycle from Slice checkpoint; preserve approved #478 native iteration and static-first outcomes. Do not add a parser, gate or state machine to enforce TDD.

Independent Implementation Review owns proactive refactoring assessment based on approved meaning and exact-head evidence. Executor still delivers minimum correct coherent implementation and repairs actual regressions; no separate self-approved REFACTOR phase. Use the existing findings transition and closure conditions for required fixes; an advisory improvement never extends scope or blocks PASS. A material spec/scope correction follows existing Lead route. Reviewer never edits reviewed files. OpenSpec Review uses shared knowledge during the existing proof loop to challenge risks already visible in planned interfaces, responsibility allocation and slice decomposition; it does not pretend to inspect future code or mandate a design pattern. Architecture depth, coupling, cohesion, locality, change amplification, seams and code smells are heuristics, not new MUST/SHALL standards or an itemized report.

Reconcile existing `agents/roles/executor.md`, `agents/roles/reviewer.md`, Implementation and both Review Skills, `openspec/config.yaml`, and the modified complete Apply-context requirement. Retain checkpoint, exact-head, Human freshness, correction and review authority. Keep protocol mechanics in the executable owner; do not promise a future CI path or modify #478 here.

## D5 — Discriminating evidence

Use the same fixed case inputs and expected consequences before/after the relevant material Skill edit (not a phrase checklist). An ordinary wording-only documentation edit without changed procedural behavior does not require these cases. Examples:

- A proposed broad slice changes multiple interfaces with tests batched at the end; contrast a vertical behavior sequence. OpenSpec Reviewer explains concrete requirement/feasibility risk only; harmless architecture choice is advisory.
- A test double missing a real required operation vs a boundary adapter implementing the contract; test a caller-visible outcome, not internal method order; preserve the original meaningful regression.
- A test tied only to obsolete implementation vs a unique safety regression; justify retirement or keep coverage, respectively.
- One test fails for absent target behavior, vs import/static/setup/unrelated failure; only the former is valid RED with test-only evidence preceding implementation. Contrast retrospective test and bulk tests. Assess provided immutable CI history rather than claim a live Python RED on N-1 for this Skill-only change.
- Verified GREEN with a proven in-scope design/test defect vs harmless naming suggestion; independent Review returns substantiated FINDINGS vs advisory, Executor corrects or supplies counterevidence, exact new head is re-reviewed; no self-clear.
- New reusable Skill content is actually read and affects the case decisions. An unchanged action boundary, missing Skill input, or fake CI evidence must not be accepted as equivalent. Validate source provenance and no alternate runtime authority.
