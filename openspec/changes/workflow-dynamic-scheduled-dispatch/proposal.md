# Change: Workflow-dynamic scheduled dispatch

## Why

The current Scheduled Tasks are externally assigned fixed roles, so handoff latency and wake ownership are coupled to three independent role schedules even though the repository already persists the legal role/action tuple. Exploration in #23 established that the repository can make durable workflow state authoritative for dispatch without adding a workflow engine, lock, lease, or new lifecycle.

Implementation experience on #21 and #25 also demonstrated an observability boundary: task markers and PR commits can prove a slice was completed, but without a bounded checkpoint on the persistent coordination Issue the workflow's progress is not reconstructable from its coordination journal alone. #21 further demonstrated that native Archive PR closing can leave the closed coordination Issue with consumed `Executor / merge-pr` routing even though the lifecycle still requires Lead terminal reconstruction.

#25 additionally exposed a termination-semantics gap: action-specific skills can describe crash recovery or remaining work in a way that permits a healthy invocation to stop even when the selected action still has immediately actionable, authorized work. The workflow therefore needs one shared work-conserving rule that distinguishes real blockers/interruption from voluntary yield without duplicating that rule across every action skill.

The same discussion exposed a Lead-role gap: when a material workflow defect appears local but may reflect a shared contract problem, Lead must actively test the reasonable blast radius instead of waiting for Human to point out sibling actions with the same root cause. This is a bounded systemic-coherence responsibility of the Lead role, not a new shared execution rule or supervisory workflow layer.

Historical coordination messages across #18, #21, and #25 exposed a related presentation and lifecycle-boundary gap. The same durable events evolved into inconsistent free-form comments, verified Slice checkpoints lacked a stable message shape, and #25 demonstrated that a persisted `READY` result can be mistaken for a completed handoff even while routing labels still point to the old owner. The workflow needs a small shared set of canonical Markdown message templates and an explicit distinction between result evidence, routing handoff, lifecycle journaling, and Human-facing delivery without introducing a messaging engine or new runtime state.

A later #25 Executor wake exposed a second execution-boundary gap. The selected `Executor / implement-change` action reached an approved 9.1 RED file mutation, the external execution environment returned a catchable safety/policy denial, and the invocation could describe that failure to the Scheduled Task conversation but left no repository-durable raw exception evidence or legal disposition path. This is not Executor-specific: any Lead, Reviewer, or Executor action can encounter a catchable tool/runtime/execution failure. The shared workflow therefore needs a narrow exception-capture and invocation-finalization contract so new failure modes can first be recorded faithfully, then diagnosed and promoted into explicit recovery paths only when evidence justifies it.

#25 then exposed a broader durable-context continuity defect. #23's authoritative exploration decision already accepted work-conserving multi-slice Executor behavior, and #25 explicitly referenced that source decision and its independent exploration gate, yet the first #25 OpenSpec revision omitted the normative behavior until later execution exposed the gap. A source reference or copied summary is therefore insufficient unless the next workflow actually dereferences the authoritative source. Within #25, revision `ea8aaa6...` introduced material exception/finalization semantics and was handed to Reviewer but not independently reviewed before a later `a225dbf...` clarification; the later Reviewer gate initially risked treating only the newest clarification as its scope until the unreviewed baseline was reconstructed. These are the same class of information-loss problem across Issue, revision, and role handoff boundaries.

## What Changes

- Add one default-branch `Scheduled-Dispatch-Mode` governance marker with `fixed-role` and `workflow-dynamic` values.
- In `workflow-dynamic` mode, make each wake reconstruct repository workflow state first and derive the invocation role/action from the single active workflow; the externally assigned legacy role becomes compatibility fallback only.
- Preserve the existing three external Scheduled Task wake slots during this migration as an external product-configuration/rollout constraint; the repository capability remains agnostic to external slot count and cadence and governs only the bootstrap behavior consumed by any wake.
- Define `Change:` persistence as the activation boundary. At most one open coordination Issue with a persisted active Change may exist; additional `Lead / propose-change` Issues with `Change: unset` remain queued pre-activation work.
- Preserve one-role-per-invocation semantics: once dispatch selects a role, handoff does not redispatch inside that invocation.
- Add one shared work-conserving selected-action contract: while the selected role/action, revision/preconditions, authority, and execution context remain current, an invocation continues immediately actionable work instead of voluntarily yielding merely because a checkpoint exists, approved local work remains, or a same-role validation failure is directly correctable. Legal termination remains limited to completed handoff/terminal result, another role or Human authority boundary, a real external asynchronous wait, genuine ambiguity/unsafe state, stale/concurrency loss, or actual tool/hard-runtime interruption.
- Add one shared authoritative-context continuity contract across all nine actions: reconstruction must preserve every still-applicable durable requirement, finding, Human clarification, execution blocker/exception, authorization, and other action-relevant evidence until an explicit contract-defined supersession, resolution, independent gate acceptance, lifecycle completion, or other legal consumption event removes it from current obligations. A newer comment, readiness result, handoff, routing tuple, or revision does not implicitly erase earlier unresolved evidence.
- Make cross-Issue provenance reconstructable: when a coordination workflow declares an authoritative source decision and/or independent source gate, Lead authoring and the applicable independent Reviewer gate must dereference those sources. A shortened coordination-Issue summary is orientation only and must not silently replace the source authority.
- Require all three revision-bound Reviewer gates to reconstruct both the exact current target revision R and the last valid independent review baseline B relevant to that gate, cover every material unreviewed change in `(B, R]`, and still evaluate the complete current state at R. Intermediate readiness/handoff/validation evidence or an unreviewed revision may replace a pending target but does not advance the reviewed baseline.
- Add one shared exception-capture contract across all Scheduled Agent engineering actions: when a tool/runtime/execution failure is catchable, persist the platform-observable raw error message first in the safety-redacted form actually returned to the Agent, together with bounded operation/revision/mutation-state evidence. Agent interpretation or classification is separate evidence and may initially remain `UNCLASSIFIED_EXECUTION_EXCEPTION`.
- Add one shared invocation-finalization contract: after a catchable exception is captured, recover and continue immediately when the current role/action can legally do so; otherwise persist a legal durable disposition and complete any required routing/handoff before a normal invocation exit. Truly uncatchable hard termination remains an at-least-once reconstruction case for a later wake.
- Keep the work-conserving, authoritative-context continuity, exception-capture, and invocation-finalization contracts in shared governance; role/action skills retain only action-specific normal results, reconstruction specializations, recovery details, blockers, and handoffs and must not duplicate or weaken the shared rules.
- Make bounded systemic coherence explicit in the Lead role: when a material finding, Human clarification, workflow failure, or specification defect may indicate a cross-cutting pattern, Lead evaluates the directly related sibling actions/contracts and chooses the narrowest correct ownership layer before settling on a local fix. This does not authorize unrelated broad audits, progress polling/supervision of Reviewer or Executor, or generalized orchestration design.
- Preserve at-least-once safety through reconstruction, idempotency where practical, revision/precondition checks, first-valid-write-wins where applicable, and stale-run termination rather than mutex/claim/lease state.
- Add minimal orphan/unexplained durable-state handling through Lead diagnosis and decision-ready Human escalation.
- Bind Human-required workflow authority to GitHub actor `royhsu-work`; other actors remain evidence-only for Human-required decisions.
- Tighten Lead Human notifications and idle exploration: at most three decision-ready proposals, no repeated unanswered notification, and idle exploration considers relevant Issues created or materially active in the preceding 7 days.
- Define `human:notified` as analytics-only metadata and keep Scheduled Task conversation/result surfacing outside repository workflow state.
- Require `review-openspec` to inspect reverse traceability first (`tasks → design → specs → proposal`), then forward traceability (`proposal → specs → design → tasks`), while keeping PASS dependent on both directions against the same exact revision.
- Require each successfully verified implementation slice to persist both satisfied task markers and exactly one bounded checkpoint comment on the persistent coordination Issue before the next slice or handoff, so completion boundaries remain reconstructable without introducing live progress state or per-mutation logging.
- Require bounded coordination-Issue journal evidence at material workflow lifecycle transitions that change durable ownership/state, including routing handoff, merge, Archive native close/post-merge terminal handoff, Lead `LIFECYCLE_COMPLETE`, and Human escalation/specification-resolution boundaries. Low-level mutations inside one legal lifecycle boundary do not independently require comments.
- Add one shared Markdown message-template contract for the recurring durable workflow events observed across #18, #21, and #25 plus the newly demonstrated catchable execution-failure evidence: `ACTION_RESULT`, `REVIEW_RESULT`, `SLICE_CHECKPOINT`, `MERGE_AUTHORIZATION`, `MERGE_RESULT`, `HANDOFF`, `HUMAN_DECISION_REQUIRED`, and `EXECUTION_EXCEPTION`. Templates define presentation and required evidence fields only; roles/skills retain authority over when each event is legally emitted.
- Make the canonical typed boundary message itself satisfy the lifecycle-journal requirement for that boundary; do not add a duplicate generic `LIFECYCLE_JOURNAL` message or recursive meta-comment solely because a typed message was emitted. `EXECUTION_EXCEPTION` is evidence of a catchable execution failure and is not automatically a lifecycle transition or action result.
- Separate result evidence from ownership transfer: when a legal result requires handoff, persisting `READY`, `PASS`, `FINDINGS`, or another action result is not normal action completion by itself. The source routing must still be fresh-read, the routing mutation must succeed, and a canonical `HANDOFF` record must durably describe the resulting owner. If an interruption occurs after the result but before handoff, the next eligible run repairs only the missing handoff/journal from durable evidence instead of repeating completed work.
- Make Human-facing scheduled delivery default-silent. Ordinary Reviewer/Executor workflow messages, `EXECUTION_EXCEPTION` evidence, and ordinary Lead progress/results remain repository-durable evidence only. Only Lead may emit `HUMAN_DECISION_REQUIRED`, and only when the current workflow genuinely requires Human authority/intent that Lead cannot resolve from the approved contract and durable evidence. External Scheduled Task delivery configuration owns actual UI/notification surfacing and must not become repository workflow state.
- Preserve native `Closes #N` linkage on the final Archive PR, but after successful authorized archive merge require Executor to fresh-read the natively closed Issue, replace consumed routing with `Lead / finalize-archive`, and journal that terminal handoff. Allow only that closed tuple as a narrow terminal-reconstruction candidate until Lead reconstructs canonical archive/default-branch state and records bounded `LIFECYCLE_COMPLETE` evidence; afterward the closed tuple is terminal history and no longer blocks later admission.
- Add a simplicity/proportionality constraint so hypothetical generality cannot justify a central dispatcher platform, message bus/template engine, generic context/event processor, generic exception/fault engine, retry state machine, or fault state machine.

## Affected Capabilities

- `scheduled-agent-workflow` — modifies scheduled dispatch, workflow activation/admission, work selection, shared selected-action termination/yield semantics, shared authoritative-context/provenance continuity, revision-bound Reviewer coverage continuity, shared catchable exception capture and invocation finalization, Reviewer OpenSpec inspection order, Executor verified-slice checkpoint observability, canonical durable workflow-message presentation, result-vs-handoff completion semantics, lifecycle-transition journaling, native-close terminal handoff/reconstruction, Human authority/notification/delivery eligibility, idle advisory, and repository governance exposure. Lead systemic coherence is implemented as a role-governance responsibility rather than a separate shared capability rule.

## Scope Boundaries

This change does not alter the nine OpenSpec lifecycle actions, role artifact authority, Reviewer independence, exact-revision gates, merge authorization, the meaning of task checkboxes as verified completion evidence, or repository-owned normal archive automation. It adds one shared selected-action continuation/termination rule, one shared authoritative-context continuity rule, one shared catchable exception-capture rule, one shared invocation-finalization rule, extends verified-slice persistence by requiring one bounded coordination-Issue checkpoint after successful VERIFY, standardizes recurring durable workflow comments through one shared Markdown template source, requires routing handoff to become durable separately from action-result evidence, requires bounded journal evidence for material workflow lifecycle transitions, and makes the existing `finalize-archive` action reachable after native close through one narrow closed-Issue terminal candidate.

Authoritative-context continuity is reconstructive rather than a new state machine. Current snapshots such as routing labels, Issue state, and PR head may use current-state semantics, while durable requirements/findings/clarifications/gates/exceptions/authorizations remain action-relevant evidence until the approved contract explicitly supersedes, resolves, accepts, completes, or consumes them. A new comment or handoff is not such an event merely because it is newer. Cross-Issue source references are dependencies to dereference, not permission to substitute a shorter summary for the authoritative decision. Reviewers additionally reconstruct a gate-specific accepted baseline and cumulative unreviewed delta, but still review the complete exact current target state rather than merely diffing commits.

The context contract does not require reading an entire Issue history on every wake when authoritative source references and valid semantic checkpoints bound the required evidence set. It also does not add an event-sourcing engine, message queue, sequence number, pending-review label, hidden context cache, generic resolver, or persistent consumption state. When authoritative provenance, review ancestry, or unresolved evidence cannot be reconstructed unambiguously, the action fails closed under existing role authority rather than guessing.

The shared work-conserving, authoritative-context, exception-capture, and invocation-finalization rules are intentionally centralized in `agents/AGENTS.md`. Individual role and skill documents only identify action-specific legal results, authority boundaries, source/baseline reconstruction specializations, waits, local recovery, and blockers; they must not restate weaker or competing generic policies. A catchable execution failure does not become permission to disappear: its observable raw evidence is captured first, then the invocation either recovers and continues or converges to a legal durable outcome and required handoff. A truly uncatchable hard kill/runtime termination may prevent current-run persistence and remains covered by later at-least-once reconstruction.

Exception capture is deliberately evidentiary rather than a fault-classification platform. The durable record preserves the raw tool/runtime message exactly as observable to the Agent after existing platform safety redaction, plus bounded factual metadata such as selected role/action, attempted operation/tool, relevant revision, whether a durable mutation completed, and the unfinished work boundary. Agent interpretation/classification is separate, may remain unclassified, and must not replace the raw evidence. The contract does not expose hidden platform data, unredact secrets, prescribe a global error taxonomy, create retry counters, or introduce generic automatic remediation.

Lead systemic coherence is intentionally role-scoped: `agents/roles/lead.md` owns the expectation that Lead performs bounded root-cause/blast-radius analysis when evidence plausibly indicates a cross-cutting workflow/specification defect. The responsibility is not copied into shared governance or every Lead skill, and it does not make Lead a supervisor over another role's valid routed work.

Workflow message standardization is deliberately presentation-level. One repository Markdown artifact owns the eight canonical template shapes; skills reference those shapes but do not copy them. The templates do not define routing, authorization, termination, review, merge, lifecycle semantics, or a global exception taxonomy and do not create a parser-dependent message bus, JSON/YAML runtime schema, template engine, status machine, or hidden workflow state. `EXECUTION_EXCEPTION` records catchable raw execution evidence and its factual context; `ACTION_RESULT` remains the legal action disposition. Free-form RED/GREEN/test-trigger progress, Lead progress polling, compatibility-correction progress, and `No Human action is required` status noise are not normalized into additional message types.

Implementation journaling is deliberately slice-boundary based: RED/GREEN/refactor/test-trigger/compatibility-correction commits, ordinary governed artifact edits, and task-marker writes inside the same not-yet-complete implementation slice do not independently require Issue comments. Git/PR remains the detailed implementation log. Canonical typed lifecycle-boundary messages are evidence, not heartbeat, progress percentage, `status:in-progress`, lock/claim/lease, retry counter, or other live runtime ownership state. A typed message that satisfies a lifecycle-journal boundary does not require a second generic journal comment.

Result and handoff evidence remain separate: a review/action result can be revision-bound evidence before ownership transfer, while `HANDOFF` records the routing transition only after the routing mutation succeeds. This distinction is not a second state machine; canonical routing labels remain the workflow owner, and crash recovery reconstructs any missing handoff from durable result evidence.

Human-facing delivery is deliberately narrower than repository evidence. Reviewer and Executor do not directly address Human through scheduled workflow delivery, ordinary Lead results remain silent externally, and `EXECUTION_EXCEPTION` is repository evidence rather than a Human notification. `HUMAN_DECISION_REQUIRED` is Lead-only and decision-required. The repository defines delivery eligibility, while actual Scheduled Task associated-conversation/notification behavior remains external product configuration and never becomes a routing or authorization predicate.

The closed terminal tuple does not create a new lifecycle action or status label: Executor performs only the post-merge routing handoff, and a later Lead invocation performs the existing `finalize-archive` reconstruction. Lead's `LIFECYCLE_COMPLETE` comment is durable execution evidence for that terminal reconstruction; canonical completion still requires the authorized Archive PR merge, correct canonical archive state, and observed closed Issue.

Reverse-first changes only the required `review-openspec` inspection order; it does not weaken or replace exact-revision bidirectional traceability. This change does not add multi-active workflow arbitration, global urgency scoring, locks/leases/heartbeats/claims, hidden in-progress state, a Human waiting state machine, extra completion/status labels, per-action copies of generic termination/context/exception/finalization semantics, Lead supervisory polling/intervention, unrelated broad audits, a generic messaging framework, a generic context/event-processing framework, a generic exception/fault platform, or a separate dispatcher configuration subsystem.

The existing three external wake slots are retained as a migration/rollout constraint owned by the external Scheduled Task product configuration. Their exact count, topology, and cadence are not repository capability state and are not modeled as repository runtime workflow state. Repository behavior defines the bootstrap and Human-delivery eligibility contract consumed by any external wake; associated-conversation/result UI likewise remains an external product boundary.
